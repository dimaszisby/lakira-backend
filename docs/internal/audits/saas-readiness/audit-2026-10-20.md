## 1. Verdict

**GOLD WITH CAVEATS (reconfirmed) — every caveat is closed on its named routes for the first time;
clean GOLD is blocked by two new P1 findings in the queue worker, X62 and X60.**

The strict ADR-001 fork-ready gate **passes**: zero P0; the six ADR-001 commands are green on Node
24 on the first run after `npm ci`; all six gated categories are at 83% or more; `LICENSE` and
`.env.example` are present.

All six caveats of ADR-008, with S1 and S2, are closed-confirmed. Each was graded closed by its
grader and reproduced:

- **C5 is closed (V3, W1).** The built server ran on Sentry 11.8 with tracing at 1.0 against a
  local listener. Requests carried a bearer token, a refresh cookie, a forwarded address, an email
  address and a query string, and one was forced into a 500. The listener received six span
  envelopes and one error event. None held an address, `net.peer.ip`, `net.host.ip`,
  `client.address`, a token, the cookie, the email address or the query. The error event's URL host
  read `[address]`, its database message `relation "[value]" does not exist`, and it carried no
  user.
- **C6, C4, C3, C2, C1, S1 and S2 are confirmed closed again**, each on a grader's grade, or for
  C1 the fork run, and a reproduction (§4.1, §5).

Two findings stand in the way, both graded P1 by the queue grader and both reproduced on a
throwaway broker and database. Under kit D-03, which follows the precedent of S1 and S2 in 2026-10,
a P1 the main thread cannot refute blocks a restated GOLD:

- **X62 (P1).** The email handlers hold one connection in a transaction and ask the pool for a
  second. With the default pool of five and a prefetch of ten, twelve queued verification emails
  stalled: five connections sat `idle in transaction`, the first email arrived after 61 s, and
  seven jobs failed into retry when Sequelize's 60 s acquire timeout fired.
- **X60 (P1).** `RabbitMQConsumer.cancel()` cancels nothing. On SIGTERM the worker logged "Consumer
  cancelled" four times, while the broker still listed the consumer 1, 2 and 4 s into the drain,
  until the channel closed.

The verdict also names the open P2 findings: X1 (a production database connection may run with TLS
verification off, and `.env.example` ships it off), X20 (`GET /metric-logs/stats` returns 500 past
about 150,000 logs), X40 and X41 (inner layers can import infrastructure by relative path or through
another feature's `public.ts`), X61 (a database failure inside `authMiddleware` answers 401 "Invalid
token") and X63 (a broker declaration mismatch takes the API process down). Each was reproduced.

## 3. Methodology

1. **Kit first.** The method (D-01) and the verdict rule (D-02) were written before a gate was run
   or a grader started. The rule for a new P1 (D-03) was written when the first P1 arrived, before
   it was reproduced.
2. **Clean install on Node 24, then the gates**, each with its exit code.
3. **Four graders**, started after the install, reading the tree and running no code. Two linted
   synthetic source on standard input, which writes nothing.
4. **Reproduction of every ground that decides the verdict**, and of the runnable P2 grounds, by the
   main thread against built or running code.
5. **Fork dry-run** on four fresh clones (§5).
6. **Appendix B scans** (§6).

Every reproduction ran on throwaway processes and services: the built server and worker from a
scratch directory with its own `.env`, so the owner's was never read; `postgres:18`,
`redis:7-alpine`, `rabbitmq:3.13-management-alpine` and `axllent/mailpit` containers on spare
loopback ports; a local listener in place of Sentry; and a stand-in mail sender with a fixed delay.
The owner's Compose stack was not written to.
