## 1. Verdict

**GOLD WITH CAVEATS — DOWNGRADED PENDING N1+N2+F1.** The repo still passes the strict
ADR-001 fork-ready gate as gauged by the prior audits, but the fresh scan revealed
**latent cross-tenant exposure in the visualization cache layer** (`viz`/`vizdash` Redis keys
scoped by `userId` only, not `organizationId`) and an **unguarded environment-variable
killswitch for all rate limiters** (`DISABLE_RATE_LIMITING=true` is accepted in
`NODE_ENV=production` with no schema rejection and only a one-shot startup log line). Both
findings are exploitable under realistic conditions: a single user who is a member of two
organizations can today see another org's visualization payloads via the cache; a misrouted
production env var silently disables every rate limiter including the auth brute-force
defenses. The prior verdict's empirical foundation (gates green, multi-tenant DB row
isolation, refresh-token rotation, fork-ready filesystem) all **hold up under re-test**, so
the repo is not regressed below previous trust levels; it is, however, **not safely shippable
as a SaaS base** until N1, N2, and F1 land. Each is ≤2h. Recommend a same-day patch
PR before any further fork or external sharing.

The six previously-tracked caveats (C1–C6) remain open-unchanged. The architecture pass also
surfaced a real contradiction with the 2026-05-24 audit's framing of Phase 5 / ADR-003 (see
§5).

## 5. Contradiction with the 2026-05-24 audit (surfaced explicitly per ground rules)

The 2026-05-24 independent audit treated Phase 5 (drift cleanup) as closed under ADR-003,
with C4 ("arch test too weak") as the only remaining tail. Reading current code, this is
not the whole picture:

- **ADR-003 mandates** `infrastructure/persistence/{models, repositories, mappers}/` as the
  canonical layout, and **names `shared/auth` as the reference slice**.
- **Auth's actual layout** is **flat** —
  `src/features/shared/auth/infrastructure/persistence/` contains seven `*RepositorySequelize.ts`
  files at the top level with only `models/` nested. There is no `repositories/` subdir.
- **Metric and metric-log do follow the ADR's nested layout**
  (`persistence/{mappers,models,repositories}/`).

So the ADR's reference slice does not match the ADR's prescribed layout, while non-reference
slices do. `.claude/rules/architecture.md` documents the nested layout as canonical. The
2026-05-24 audit acknowledged this only obliquely via C4 (the arch test does not detect it).
Surfacing here so the disagreement is recorded, not quietly inherited.

**Recommendation:** add a follow-on ADR pinning one shape (and migrate the other), or
explicitly update ADR-003 to mark `shared/auth` as the canonical _flat_ shape and require
new slices to match that. Either choice is fine; the current state is not.

### 6.1 P0 — cross-tenant cache scoping

#### N1 — Visualization cache keys are scoped by `userId`, not `organizationId`

- **File:** `src/features/public/analytics/infrastructure/cache/VisualizationCacheRedis.ts:52–69`
- **Evidence (verbatim):**
  ```ts
  function vizKey(input: SingleVizCacheKey) {
    const raw = `${input.userId}|${input.metricId}|${input.bucketIso}|${input.startISO}|${input.endISO}|${input.tz}|${input.fill}`;
    // ...
    return `viz:${input.userId}:${input.metricId}:${input.bucketIso}:${hash}`;
  }
  function vizDashKey(input: DashboardVizCacheKey) {
    const raw = `${input.userId}|${input.metricIds.join(",")}|${input.bucketIso}|...`;
    return `vizdash:${input.userId}:${input.bucketIso}:${hash}`;
  }
  ```
  `organizationId` is present on the port type (`SingleVizCacheKey`) and flows into the
  read repository (`VisualizationReadRepoSequelize.fetchVisualization`, `:84–95`), but **never
  enters the cache key or the hashed raw string**.
- **Why prior audits missed it.** 2026-05-24 verified that the SQL `WHERE` clauses scope by
  `organizationId` (they do). It did not inspect the cache layer. Cache keys are a separate
  tenant boundary that must be enforced independently of the DB.
- **Failure mode.** A user who is a member of two organizations queries `metric-123` in
  Org-X (their active org). Result cached under `viz:UserA:metric-123:...`. User switches
  active org to Org-Y. If a metric with the same UUID exists in Org-Y (rare but possible via
  the cross-org public metric reference `MetricRepoSequelize.originalMetricExists`, which is
  intentionally org-unscoped per the 05-24 "possible issues"), the cache returns Org-X's
  series for an Org-Y request. More broadly, the dashboard key `vizdash:${userId}:${bucketIso}:${hash}`
  is keyed only by user — any state stored there persists across org switches.
- **Priority:** **P0.** Silent cross-tenant disclosure on cache hit. **Effort:** ≤1h.
- **Fix:** Include `organizationId` in both the visible key prefix and the hashed raw string.

#### N2 — `VisualizationInvalidationAdapter` signature has no `organizationId`

- **File:** `src/features/public/analytics/infrastructure/cache/VisualizationInvalidationAdapter.ts:6–26`
- **Evidence:** `invalidateByMetric(userId: string, metricId: string)` scans
  `viz:${userId}:${metricId}:*` and `vizdash:${userId}:*`. The port signature does not take
  `organizationId`. After N1 is fixed, this adapter will **fail to match** the new key
  shape. Conversely, today, mutating a log in Org-X invalidates the user's dashboard cache
  for **every** org they belong to (`vizdash:${userId}:*`) — a correctness gap plus a leak
  surface as soon as caches contain cross-org state.
- **Priority:** **P0** (must land together with N1). **Effort:** ≤1h.
- **Fix:** Extend `VisualizationInvalidationPort.invalidateByMetric(userId, organizationId, metricId)`
  and thread `organizationId` through every call site (`MetricLogCacheRedis.invalidate` at
  `src/features/public/metric-log/infrastructure/cache/MetricLogCacheRedis.ts:48` and the
  analytics use-cases that publish invalidation events).

### 6.2 P1 — high-impact gaps

#### N3 — Cache-key org-scoping is systemic, not isolated to viz

- **Files:**
  - `src/features/public/metric/infrastructure/cache/MetricCacheRedis.ts:16–18` —
    `metrics:${userId}:*`, `metric:${userId}:${metricId}:*`
  - `src/features/public/metric-log/infrastructure/cache/MetricLogCacheRedis.ts:36–52` —
    `logs:${userId}:${metricId}:*`, `logStats:${userId}:${metricId}`, `log:${userId}:${logId}`
  - `src/shared/cache/keys.ts:32–51` — `buildCursorCacheKey` makes `userId` the only
    required segment; `organizationId` is an optional `segments` entry.
- **Impact today:** `metric-category/application/queries/ListCategories.ts:22` _does_ include
  `organizationId` as a labelled segment, so that path is safe. But the port surface is
  structurally vulnerable — any future feature that wraps a list query in `metric` or
  `metric-log` caching without remembering to pass `organizationId` will inherit a
  cross-tenant bug identical to N1.
- **Priority:** **P1.** **Effort:** ≤1d.
- **Fix:** Make `organizationId` a first-class required parameter of `buildCursorCacheKey`
  and the metric/metric-log cache key helpers. Add an architecture-test rule that fails CI
  if any cache key template contains `${userId}` without a sibling `${organizationId}`.

#### N4 — RabbitMQ messages don't propagate `x-request-id`; consumer doesn't enter ALS

- **Files:**
  - `src/shared/infrastructure/queue/RabbitMQPublisher.ts:39–60` (publish path) — no caller
    reads `getRequestId()` from ALS into `properties.headers`.
  - `src/shared/infrastructure/queue/RabbitMQConsumer.ts:32–48` (consume path) — handler
    invoked directly, not wrapped in `requestIdStorage.run(...)`.
  - `src/features/public/metric-log/application/use-cases/GenerateDummyMetricLogsHandler.ts:22–43`
- **Failure mode:** An HTTP request publishes a `metric-log.generate-dummy` job. Worker logs
  show `requestId: undefined`. First production incident on the worker, on-call cannot
  correlate worker logs back to the originating HTTP call.
- **Priority:** **P1.** **Effort:** ≤1d.
- **Fix:** Publisher auto-reads `getRequestId()` from ALS and sets
  `properties.headers["x-request-id"]`. Consumer wraps `handler(msg)` in
  `requestIdStorage.run(msg.properties.headers["x-request-id"] ?? randomUUID(), () => ...)`.

#### N5 — OpenAPI spec omits two `dummy` routes mounted in code

- **Files:**
  - Code mounts: `src/features/public/metric/infrastructure/http/router.ts` →
    `POST /metrics/dummy`; `src/features/public/metric-category/.../router.ts` →
    `POST /metric-categories/dummy`. (`metric-log/.../dummy` is documented.)
  - Spec: `docs/reference/api/lakira-backend-openapi.json` lacks the first two.
- **Why prior audits missed it.** The 05-24 spec-drift check tested _that the generator
  runs deterministically_ (`git diff` byte-identical) — it did not test that every router
  is registered with the generator. Conditionally registered dummy endpoints drop out.
- **Impact:** Contract drift; Schemathesis cannot fuzz endpoints it doesn't know about, so
  any "API contract coverage" claim is overstated.
- **Priority:** **P1.** **Effort:** ≤1d.
- **Fix:** Gate the dummy routes behind a router-level `NODE_ENV !== "production"` skip
  _and_ register their Zod schemas with the OpenAPI generator. Document the gate.

#### F1 — `DISABLE_RATE_LIMITING` has no `NODE_ENV=production` guard (**HIGH severity**)

- **File:** `src/config/zodEnv.ts:188–191`
  ```ts
  DISABLE_RATE_LIMITING: z
    .string()
    .transform((val) => val === "true")
    .default("false"),
  ```
- **Risk:** A misconfigured production deploy (fat-finger, CI copying a test `.env`, a
  forker who didn't clean their `.env`) silently disables every rate limiter — global,
  user, analytics, switch-org, password-reset, email-verify. Brute force on `/auth/login`,
  credential stuffing, and scraping become unconstrained. The one-shot `logger.info` notice
  at `src/shared/middleware/rate-limiter.ts:10` may be missed by log monitoring; there is
  no startup-time refusal.
- **Why prior audits missed it.** The flag is correctly documented as "test/fuzzing only" in
  the rules and the code; the rules-as-convention enforcement is not backed by schema
  refusal. Prior audits treated the convention as enforcement.
- **Priority:** **P1 / HIGH.** **Effort:** ≤30 min.
- **Fix:**
  ```ts
  DISABLE_RATE_LIMITING: z
    .string()
    .transform((val) => val === "true")
    .default("false")
    .superRefine((val, ctx) => {
      if (val && process.env.NODE_ENV === "production") {
        ctx.addIssue({
          code: z.ZodIssueCode.custom,
          message: "DISABLE_RATE_LIMITING cannot be true in production",
        });
      }
    }),
  ```
