## 1. Verdict

> **Dated snapshot (banner added 2026-09-24).** §§ 1–3 grade the code as it stood on 2026-08-17 and
> are kept as written. Several findings have closed since — Factor XI's P0 among them. **§ 4 is the
> only live section:** read it for what is still open.

**PARTIALLY COMPLIANT — THREE VIOLATIONS, ONE ROOT CAUSE.** The application layer scores well:
config is centralised behind a 65-key Zod schema with only four raw `process.env` reads outside
`src/config/`, the process model is genuinely stateless, port binding is self-contained, shutdown
drains all three backing services, and migrations are correctly separated as one-off admin steps.
Five factors pass cleanly.

The three violations — **V (Build/release/run)**, **VIII (Concurrency)**, and **XI (Logs)** — are
not three independent defects. They are one unfinished piece of work seen from three angles: **the
deployment topology was never completed.** A well-built multi-stage `Dockerfile` exists that CI
never builds. A well-built worker process exists that nothing runs. A well-built structured logger
exists whose output, in production, goes to files nobody collects. In each case the artifact is
sound and its connection to how the system actually ships is missing.

That framing matters for remediation sequencing: fixing them together is substantially cheaper than
fixing them separately, because all three terminate at the same question — what does a Lakira
release consist of, and what runs it.

**Bearing on the pending observability decision.** The OTel/Prometheus/Loki/Grafana/Tempo choice
(optional Compose profile vs. baked into default config) cannot be answered on its own terms yet.
Factor XI shows there is currently **no log stream for Loki to collect** — production writes to
local files and emits nothing to stdout. Deciding the shipping mechanism for a collector before the
telemetry it collects exists would be premature. [ADR-0041](../../../explanation/decisions/adr-0041-logs-as-event-streams-on-stdout.md)
is therefore a prerequisite of [ADR-0038](../../../explanation/decisions/adr-0038-observability-stack-as-attached-backing-service.md),
not a parallel concern.

## 3. Factor entries

### Factor I · Codebase — one codebase tracked in revision control, many deploys (Compliant)

- **Status:** Pass
- **What the code does:** One repository (`origin git@github.com:dimaszisby/lakira-backend.git`),
  one application (`find . -maxdepth 3 -name package.json -not -path "*/node_modules/*"` returns
  only the root). Three long-lived branches — `dev` → `staging` → `main` — map to three deploys via
  branch-gated CI jobs (`backend-ci.yml:365` `if: github.ref == 'refs/heads/staging'`,
  `backend-ci.yml:438` `if: github.ref == 'refs/heads/main'`). This is the canonical
  one-codebase-many-deploys shape.
- **Gap:** None material. Two observations recorded for completeness, neither a violation:
  1. No build artefacts are tracked — 828 files in `git ls-files`, and `dist/`, `logs/`, `coverage/`,
     `tmp/`, `graphify-out/`, `.venv-*/`, `.hypothesis/` are all gitignored and confirmed at zero
     tracked files each.
  2. The repo is explicitly a fork template (`scripts/bootstrap-fork.sh`). Forking produces
     divergent codebases from a shared ancestor, which is a deviation at the _template_ level rather
     than the deploy level. Factor I governs one app's deploys; this is out of its scope. Noted so a
     future auditor does not re-litigate it.
- **Recommended fix:** None.
- **Effort:** —
- **Evidence:** `git ls-files | wc -l` → `828`; `git ls-files dist logs coverage tmp graphify-out`
  → no output. `.gitignore:17-21` excludes `.env`, `.env.development`, `.env.production`,
  `.env.staging`, `.env.test`; only `.env.example` and `.env.test.example` are tracked.

### Factor II · Dependencies — explicitly declare and isolate dependencies (Partial)

- **Status:** Partial — P2
- **What the code does:** Strong on the fundamentals. `package-lock.json` is committed and every
  install path uses it: `Dockerfile:5` `RUN npm ci`, `Dockerfile:15` `RUN npm ci --omit=dev`, and
  all seven CI jobs `run: npm ci`. Node is pinned to 20 in five places that agree — `.nvmrc`,
  `.node-version`, `package.json` `engines`, `Dockerfile:2`/`:10` (`FROM node:20-alpine`), and
  `backend-ci.yml:24` (`NODE_VERSION: 20`). The Python test-time dependency is properly isolated
  rather than implicit: `tests/contract/schemathesis/requirements.txt` pins `schemathesis==4.4.4`,
  installed by a dedicated `actions/setup-python` step, and never referenced from `package.json` or
  either Dockerfile.
- **Gap:** Two devDependencies are invoked by scripts that claim to be production entrypoints.
  `sequelize-cli` (`package.json:147`) is called by `start:staging` (`package.json:10`), and
  `ts-node` (`package.json:150`) is called by `staging` (`:16`), `prod` (`:17`), and
  `worker:staging` (`:15`). The runtime image installs with `npm ci --omit=dev`
  (`Dockerfile:15`), so none of these would resolve inside it.
  Separately, `start:staging` has a plain argument-order defect: `--migrations-path src/migrations`
  is appended to the `node dist/server.js` invocation rather than to `sequelize-cli`, so the
  migration half runs without it and the server receives a stray argument.
- **Why it matters:** Latent rather than active — the actual deploy path never executes these
  scripts (`Dockerfile:18` runs `CMD ["node", "dist/server.js"]`, and CI runs migrations on the
  Actions runner with a full `npm ci`). The cost is that four scripts named for production
  environments are untested, non-functional in the runtime image, and will mislead whoever first
  reaches for them during an incident.
- **Recommended fix:** Delete `staging`, `prod`, and `start:staging`; they duplicate `start` and
  `migrate:staging:ci`, which are the paths that actually run. Keep `worker:dev`. Replace
  `worker:staging` with the compiled equivalent of `worker` once
  [ADR-0040](../../../explanation/decisions/adr-0040-worker-process-deployment-topology.md) settles
  the worker's deployment. If any are kept, move `ts-node` and `sequelize-cli` to `dependencies`.
- **Effort:** S
- **Evidence:** `package.json:10` —
  `"start:staging": "NODE_ENV=staging npx sequelize-cli db:migrate --config src/config/config.cjs && NODE_ENV=staging node dist/server.js --migrations-path src/migrations"`.
  `package.json:147` `"sequelize-cli": "^6.6.2"` and `:150` `"ts-node": "^10.9.2"`, both under
  `devDependencies`.

### Factor III · Config — store config in the environment (Partial)

- **Status:** Partial — P1
- **What the code does:** This is the best-engineered factor in the codebase. A single Zod schema
  (`src/config/zodEnv.ts`, 65 keys) validates every variable; `loadEnvOrExit()`
  (`src/config/envManager.ts:83-96`) memoises the result and fails fast with a structured
  `[ENV_ERROR]` on invalid input. Discipline holds at the call sites: across all of `src/`, only
  **four** `process.env` reads exist outside `src/config/` — two in a test helper, one in
  `logger.ts:7`, one in `server.ts:74`. Secrets never reach the repo (`.gitignore:17-21`) and
  sensitive values are masked in logs via `SENSITIVE_KEY_PATTERN`
  (`src/config/sensitive-keys.ts`).
- **Gap:** Four issues, in descending order of consequence.
  1. **Config is grouped into named environments** — the specific anti-pattern Factor III names.
     `DATABASE_URL_KEYS` (`zodEnv.ts:368-373`) maps `NODE_ENV` to one of
     `DEVELOPMENT_DATABASE_URL` / `TEST_DATABASE_URL` / `STAGING_DATABASE_URL` /
     `PRODUCTION_DATABASE_URL`, and `normalizeDatabaseConfig` (`:375-423`) selects among them at
     boot. A deploy should read `DATABASE_URL`; it should not need to know which named environment
     it is impersonating to find its own database.
  2. **Environment-conditional defaults are compiled into the schema.** `zodEnv.ts:75-77` defaults
     `DB_HOST` to `"db"` under test and `"127.0.0.1"` otherwise; `:90-92` does the same for
     `REDIS_HOST`; `:104-107` for `REDIS_REQUIRED`; `:157` for `ENABLE_DUMMY_ENDPOINTS`; `:258` for
     `EMAIL_PROVIDER`. Each reads raw `process.env.NODE_ENV` inside the schema module. Some of this
     is an unavoidable bootstrap ordering constraint, but the effect is that per-environment
     behaviour lives in code rather than in the environment.
  3. **One variable escapes validation entirely.** `server.ts:74` reads
     `process.env.SKIP_DB_LIFECYCLE === "true"` directly. It appears in neither `zodEnv.ts` nor
     `.env.example`, so it is undocumented, untyped, and invisible to the fail-fast contract — while
     controlling whether the database bootstrap runs at all.
  4. **A second, unvalidated config module.** `src/config/config.cjs` (used by `sequelize-cli`)
     performs 19 raw `process.env` reads and duplicates `src/config/db.ts`. They have already
     drifted on SQL logging: `config.cjs` uses `console.log` for development where `db.ts` routes
     through the Winston `sqlLogger` (`db.ts:17`).

- **Why it matters:** (1) and (2) are what make a fork or a new environment expensive — a fourth
  deploy target requires a schema change, not just new env values. (3) is the sharper operational
  risk: an unvalidated switch that skips DB bootstrap has no guard preventing it from being set in
  production, which is precisely the class of defect
  [ADR-0036](../../../explanation/decisions/adr-0036-refuse-production-unsafe-env-switches.md)
  already exists to prevent — `SKIP_DB_LIFECYCLE` should be on its list and is not.
- **Recommended fix:** Add `SKIP_DB_LIFECYCLE` to `zodEnv.ts` and to ADR-0036's refused-in-production
  table (S — do this first and independently; it is a straightforward safety fix, not a trade-off).
  Then collapse the four per-environment DB URL keys to `DATABASE_URL` alone, keeping the old keys
  as deprecated optional aliases for one release (M). `config.cjs` cannot import the ESM schema, so
  the duplication is structural — the achievable fix is a comment in both files pointing at each
  other plus a unit test asserting the two produce identical connection settings for a given env (S).
- **Effort:** S for the safety fix, M for the rest.
- **Evidence:** `src/server.ts:74` —
  `const skipDbBootstrap = process.env.SKIP_DB_LIFECYCLE === "true";`.
  `src/config/zodEnv.ts:368-373` — the `DATABASE_URL_KEYS` map.
  `grep -rn "process\.env\." src/ --include="*.ts" | grep -v "^src/config/"` → 4 matches.

### Factor IV · Backing services — treat backing services as attached resources (Partial)

- **Status:** Partial — P1 · → [ADR-0038](../../../explanation/decisions/adr-0038-observability-stack-as-attached-backing-service.md)
- **What the code does:** Attachment is done properly for all three stateful services. Postgres,
  Redis, and RabbitMQ are each addressed by URL or by env-composed host/port with no hardcoded
  production endpoints — `normalizeDatabaseConfig` (`zodEnv.ts:375-423`),
  `src/utils/redis-client.ts:7-21`, and `buildAmqpUrl()`
  (`src/shared/infrastructure/queue/RabbitMQConnection.ts:7-13`). TLS is forced for staging and
  production (`src/config/db.ts:42-61`).

  The abstraction layer is better than a first pass suggests. `MessageQueuePort`
  (`src/shared/application/ports/MessageQueuePort.ts:11`) has two adapters — `RabbitMQPublisher` and
  `NoopMessageQueue` — so the queue can be detached entirely via `RABBITMQ_ENABLED` with no
  application-layer change. `CachePort<T>` (`src/shared/application/ports/CachePort.ts`) plus
  per-slice `CachePort` interfaces in four features mean cache access from the application layer is
  behind a port too, with Redis adapters implementing it. Swapping either backing service is a
  contained change.

- **Gap:** Three items, all narrower than "no abstraction".
  1. **No observability backing service is attached at all.** `grep -rniE "@opentelemetry|prom-client|prometheus"`
     across `src/` and `package.json` returns nothing. `@sentry/node` is the sole telemetry
     integration, and it covers errors, not metrics or traces. Meanwhile `docker-compose.yml:66`
     already publishes RabbitMQ's Prometheus metrics port `15692` and nothing scrapes it — the
     socket is open and unused. **This is the gap the pending stack decision has to close, and it is
     the reason ADR-0038 exists.**
  2. **The middleware tier bypasses the port layer.** `src/shared/middleware/rate-limiter.ts` and
     `src/shared/middleware/cache.ts` import `redisClient` directly. Being HTTP middleware they sit
     outside the DDD layering, so this is defensible, but it means the rate limiter holds its own
     view of Redis availability — see (3).
  3. **The rate limiter can silently detach its backing store.** `maybeCreateStore()`
     (`rate-limiter.ts:21-34`) returns `undefined` when `!env.REDIS_REQUIRED && !redisClient.isOpen`,
     which makes `express-rate-limit` fall back to its built-in per-process in-memory store. All
     eight limiters share this path. **Production is safe by default** — `REDIS_REQUIRED` defaults
     to `"true"` outside test (`zodEnv.ts:104-107`), so the fallback is opt-in and it does log a
     warning. But when opted into, a shared attached resource silently becomes per-process state,
     and rate limits become N× looser across N instances.

  A fourth, minor: `src/features/shared/auth/feature.ts:62` reaches the lockout client via
  `redisClient as unknown as LockoutRedisClient` — a type-level escape hatch where the other three
  consumers have real ports.

- **Why it matters:** The first item is the whole subject of the pending decision. The third is the
  one that bites at scale: it converts a correctness property (rate limits) into a
  deployment-topology-dependent one, and the only signal is a `logger.warn` that — per Factor XI —
  currently goes to a file nobody reads.
- **Recommended fix:** For (1), see
  [ADR-0038](../../../explanation/decisions/adr-0038-observability-stack-as-attached-backing-service.md);
  it is a real trade-off and this audit does not pre-empt it. For (3), make the fallback explicit
  rather than inferred: a `RATE_LIMIT_STORE` env var with values `redis` / `memory`, refusing
  `memory` under `NODE_ENV=production` via the ADR-0036 mechanism (S). For (4), define a
  `LockoutStorePort` mirroring `CachePort` (S).
- **Effort:** S for (3) and (4); (1) is sized by ADR-0038.
- **Evidence:** `src/shared/middleware/rate-limiter.ts:21-29` —
  `if (!env.REDIS_REQUIRED && !redisClient.isOpen) { logger.warn("[RATE LIMITER] Redis not connected; falling back to in-memory store."); return undefined; }`.
  `docker-compose.yml:66` — `- "15692:15692" # Prometheus metrics`.
  `grep -rniE "@opentelemetry|prom-client" src/ package.json` → no match.

### Factor V · Build, release, run — strictly separate build and run stages (Violated)

- **Status:** Fail — P1 · → [ADR-0039](../../../explanation/decisions/adr-0039-release-identity-and-immutable-artifacts.md)
- **What the code does:** The `Dockerfile` is exemplary and should be preserved as-is. It is
  genuinely multi-stage: `npm run build` executes only in the build stage (`Dockerfile:7`), and the
  runtime stage copies `dist/` plus `package*.json` and installs with `npm ci --omit=dev`
  (`:13-15`), so no TypeScript source and no devDependencies reach the image. It runs as
  `USER node` (`:16`) with `dumb-init` as PID 1 (`:17`) so signals reach the Node process. No config
  is baked in — `.dockerignore` excludes `.env*`, and the Dockerfile sets no application `ENV`.
- **Gap:** **CI never builds this image, and nothing ever deploys it.** The `deploy_staging` and
  `deploy_production` jobs run `npm run build` on the Actions runner
  (`backend-ci.yml:387`, `:485`), then discard the output, run migrations, and finish with
  `curl -X POST "$RENDER_..._DEPLOY_HOOK_URL"` (`:398`, `:496`). Render then performs its own build
  from source. The artefact CI validated is therefore never the artefact that serves traffic; two
  independent builds of the same commit are, at best, coincidentally identical.

  Compounding this, **no release identity exists anywhere in the system.** `grep -rniE
"GIT_SHA|COMMIT_SHA|APP_VERSION|npm_package_version|release:"` across `src/` returns nothing.
  `package.json:3` carries a static `"version": "1.0.0"` that no runtime code reads, and
  `Sentry.init` (`server.ts:56-62`) sets `dsn`, `tracesSampleRate`, and `environment` but **no
  `release`** — so no Sentry error can be attributed to a build.

- **Why it matters:** The release stage of build/release/run effectively does not exist. Three
  concrete consequences: a rollback cannot be performed by redeploying a known-good artefact,
  because none is retained; "which code was running when this broke?" is unanswerable from the error
  report; and a green CI run is not evidence about the bytes in production, only about a build of
  the same source performed elsewhere.
- **Recommended fix:** See
  [ADR-0039](../../../explanation/decisions/adr-0039-release-identity-and-immutable-artifacts.md) —
  the choice between keeping Render's source build and moving to a registry-published image is a
  real trade-off with cost on both sides. Independent of it, one fix is unambiguous and should land
  regardless: stamp a release identity. Pass the commit SHA in as an env var, surface it on
  `/api/v1/health`, and set it as `Sentry.init({ release })`. That is ~10 lines and answers the
  "what was running" question even if the build topology never changes.
- **Effort:** S for release stamping; M–L for the artefact change, sized by ADR-0039.
- **Evidence:** `.github/workflows/backend-ci.yml:485-496` — `run: npm run build`, then
  `run: npm run migrate:production:ci`, then `curl -X POST "$RENDER_PRODUCTION_DEPLOY_HOOK_URL"`,
  with no `docker build` or registry push anywhere in the file.
  `src/server.ts:56-62` — `Sentry.init({ dsn, tracesSampleRate, environment })`, no `release`.

### Factor VI · Processes — execute the app as stateless processes (Compliant)

- **Status:** Pass
- **What the code does:** Authentication is stateless JWT throughout — `JwtTokenProvider` signs and
  verifies, and there is no `express-session`, no `connect-redis`, and no server-side session store
  anywhere in `src/`. No module-level mutable state survives a request: every `new Map()`/`new Set()`
  in `src/` is either per-call (`ListOrganizationMembers.ts:30`, `SwitchOrganization.ts:49`) or a
  constant lookup table (`method-guard.ts:26`). There is no in-process scheduler — the only two
  timer calls are scoped to a single operation each (`server.ts:157`, the 2 s readiness budget, and
  `RabbitMQConsumer.ts:103`, a per-message ack timer). All durable state lives in Postgres; all
  ephemeral shared state lives in Redis.
- **Gap:** One, already recorded under Factor IV rather than double-counted here: the rate limiter's
  opt-in in-memory fallback (`rate-limiter.ts:21-34`) is the single code path that would introduce
  per-process state. It is off by default in production.
- **Recommended fix:** None beyond the Factor IV item.
- **Effort:** —
- **Evidence:** `grep -rn "express-session\|connect-redis\|new session(" src/` → no match.
  `grep -rnE "setInterval|setTimeout" src/ --include="*.ts"` → 2 matches, both operation-scoped.

### Factor VII · Port binding — export services via port binding (Compliant)

- **Status:** Pass
- **What the code does:** The app is fully self-contained. `src/server.ts:246-249` binds directly —
  `const PORT = env.PORT || 5000; server = app.listen(PORT, ...)` — with `PORT` coming from the
  validated schema (`zodEnv.ts:18-27`, default `"5000"`). No external webserver is injected; the
  container's `CMD ["node", "dist/server.js"]` (`Dockerfile:18`) binds the port itself. Proxy
  awareness is configurable rather than assumed (`server.ts:95`,
  `app.set("trust proxy", env.TRUST_PROXY ?? 1)`).

  Both orchestrator probes exist and are correctly separated. `/api/v1/health` (`:143-149`) is a
  dependency-free liveness check; `/api/v1/ready` (`:152-178`) races `sequelize.authenticate()` and
  `redisClient.ping()` against a 2 s budget and returns 503 with a per-dependency breakdown when
  either fails. Both are registered **before** the global rate limiter (`:181`), so an overloaded
  instance still answers its probes — a detail that is easy to get wrong and was got right.

- **Gap:** None. One inconsistency worth noting for Factor X rather than here: the app binds 5000 by
  default, but `docker-compose.yml:98` publishes `"8001:8001"`.
- **Recommended fix:** None.
- **Effort:** —
- **Evidence:** `src/server.ts:246` — `const PORT = env.PORT || 5000;`.
  `src/server.ts:142` — `// Health check — registered before rate limiter so probes are never throttled`.

### Factor VIII · Concurrency — scale out via the process model (Violated)

- **Status:** Fail — P1 · → [ADR-0040](../../../explanation/decisions/adr-0040-worker-process-deployment-topology.md)
- **What the code does:** The web tier is correctly shaped for horizontal scaling. There is no
  in-app clustering (`grep` for `cluster`, `pm2`, `worker_threads` across `package.json`,
  `Dockerfile*`, and `docker-compose*.yml` returns nothing), which is the right call — one process
  per container, scaled by the platform, is the twelve-factor unit. Combined with stateless auth
  (Factor VI) and externalised state (Factor IV), adding web instances requires no code change.

  A second process type is fully implemented. `src/worker.ts` is a standalone RabbitMQ consumer with
  its own DB connection (`:28-30`), its own signal handlers, and a correct drain-before-close
  shutdown that closes consumers first, then the broker, then Postgres (`:51-68`). It refuses to
  start without `RABBITMQ_ENABLED` (`:16-21`).

- **Gap:** **Nothing runs the worker.** `package.json` declares three scripts for it — `worker`
  (`:13`), `worker:dev` (`:14`), `worker:staging` (`:15`) — and that is the entirety of its
  operational existence. `grep -rn "worker" docker-compose.yml docker-compose.test.yml Dockerfile
Dockerfile.dev .github/workflows/` returns **no matches**: no Compose service, no Dockerfile `CMD`
  variant, no CI job, and no Render service. The only container command is
  `CMD ["node", "dist/server.js"]`.

  The documentation asserts otherwise. `docs/explanation/architecture/c4-containers.md:3` describes
  "two deployable processes sharing one codebase and one database," and its table gives the worker a
  `Start` command and a `Scales on` axis. That is a description of an intended design, not of the
  running system.

- **Why it matters:** The async tier cannot execute in any environment as configured. Any message
  published to `QUEUES.METRIC_LOG_GENERATE_DUMMY` accumulates unconsumed. Because `RABBITMQ_ENABLED`
  gates publishing too (`server.ts:52`, `:240-243`), the feature is simply inert rather than broken
  — but the moment the flag is turned on in a deployed environment, work is queued and never
  consumed. The concurrency model has one axis where the architecture claims two.
- **Recommended fix:** See
  [ADR-0040](../../../explanation/decisions/adr-0040-worker-process-deployment-topology.md) — the
  options (separate Render service, in-web-process consumer, or removing the tier until there is
  load to justify it) have materially different cost and operational profiles. Independent of that
  decision, correct `c4-containers.md` now so the diagram stops describing an untrue topology; that
  change is in this audit's scope and is applied (§9).
- **Effort:** S to correct the docs; the deployment change is sized by ADR-0040.
- **Evidence:** `grep -rn "worker" docker-compose.yml docker-compose.test.yml Dockerfile Dockerfile.dev .github/workflows/`
  → no match. `Dockerfile:18` — `CMD ["node", "dist/server.js"]`.
  `package.json:13` — `"worker": "NODE_ENV=production node dist/worker.js"`.

### Factor IX · Disposability — fast startup and graceful shutdown (Compliant)

- **Status:** Pass — with P2 observations
- **What the code does:** Shutdown is handled thoroughly. `SIGTERM` and `SIGINT`
  (`server.ts:295-297`) route to a `shutdown()` (`:263-292`) that closes the HTTP server, then
  Sequelize, then Redis, then RabbitMQ when enabled — in that order, awaiting each. `dumb-init` as
  PID 1 (`Dockerfile:17`) ensures the signal actually arrives, which is the usual failure mode for
  containerised Node. `src/worker.ts:51-68` mirrors the pattern and additionally drains in-flight
  consumers before disconnecting. Startup is cheap: no migrations run at boot, and `loadModels()`
  plus `authenticate()` are both idempotent.
- **Gap:** Two P2 observations, neither affecting correctness today.
  1. `sequelize.authenticate()` runs twice per boot — once at module load via `initialDbBootstrap`
     (`server.ts:75-89`) and again inside `startServer()` (`:237`). A redundant round-trip on a cold
     start.
  2. `uncaughtException` and `unhandledRejection` (`:300-313`) both invoke the full graceful
     `shutdown()`. Draining connections from a process in unknown state is a debatable choice — the
     conventional guidance is to log, then exit fast and let the orchestrator replace the instance,
     since handler code running after an unknown corruption can itself fail or hang. `exitOnError:
false` on the logger (`logger.ts:69`) reinforces the same posture.
- **Why it matters:** Neither is urgent. (2) matters most in the case it is designed for: if the
  shutdown path itself throws after an `uncaughtException`, the process sets `process.exitCode = 1`
  (`:290`) but does not call `process.exit()`, so it can linger without serving.
- **Recommended fix:** Drop the module-level `initialDbBootstrap` call and let `startServer()` own
  connection setup, keeping the `serverReady` export for tests (S). Separately, give the fatal
  handlers a bounded shutdown — a `setTimeout(() => process.exit(1), 5000).unref()` guard so a hung
  drain cannot keep a broken process alive (S).
- **Effort:** S
- **Evidence:** `src/server.ts:86` — `const serverBootstrapPromise = initialDbBootstrap().catch(...)`
  at module scope, and `:237` — `await sequelize.authenticate();` inside `startServer`.
  `src/server.ts:300-303` — `process.on("uncaughtException", (error) => { logger.error(...); shutdown("Uncaught Exception"); });`

### Factor X · Dev/prod parity — keep development, staging, and production as similar as possible (Partial)

- **Status:** Partial — P1
- **What the code does:** One real strength: `docker-compose.test.yml:23` builds the **production**
  `Dockerfile`, so the CI compose path exercises the same image shape that ships. That is better
  parity than most projects manage, and it should be preserved.
- **Gap:** Four divergences.
  1. **Three-way backing-service version drift.** Dev runs `postgres:17-alpine`
     (`docker-compose.yml:3`) and `redis:alpine` (`:34` — **entirely unpinned**, floating to whatever
     `latest` resolves to at pull time). CI runs `postgres:15` (`backend-ci.yml:121`) and `redis:7`
     (`:135`). Production is Render-managed, and its versions are not declared anywhere in the repo.
     A major-version gap between the database developers write against and the one CI tests against
     is a real class of bug — Postgres 15→17 changed planner behaviour and several defaults.
  2. **RabbitMQ is absent from CI entirely.** It is defined in `docker-compose.yml:53` but there is
     no `rabbitmq` service in any CI job. The queue path — publisher, consumer, topology, DLX,
     idempotency table — is never exercised against a live broker in CI. Given Factor VIII, it is
     never exercised in a deployed environment either.
  3. **`docker compose up` does not work as documented.** `docker-compose.yml:86` sets
     `env_file: .env.development`. That file does not exist in the repo and is gitignored
     (`.gitignore:18`), while `README.md:28` instructs `cp .env.example .env`. The two are
     inconsistent, and the `app` service fails to start on a clean clone. The port mapping compounds
     it: compose publishes `"8001:8001"` (`:98`) while the app binds 5000 by default.
     `docker-compose.test.yml:5-8` separately hardcodes `lakira_user` / `lakira_password` /
     `lakira_test_db`, which also defeats `bootstrap-fork.sh`'s renaming.
  4. **A stale comment asserts the opposite of the code.** `Dockerfile.dev:1-10` states it is used by
     `docker-compose.test.yml`; that file actually builds the production `Dockerfile` (`:23`). The
     behaviour is the good one — only the comment is wrong, and it will mislead the next reader into
     "fixing" the parity strength.

- **Why it matters:** (3) is the immediate cost — the documented first-run path for a new contributor
  or a forker is broken, which is expensive for a repo whose stated purpose is being forked. (1) and
  (2) are the risk-carrying ones: a green CI run is weaker evidence than it appears, because it ran
  against a different major version of Postgres and no broker at all.
- **Recommended fix:** Pin every image to the same version triple across dev and CI, and record the
  Render-managed versions in `docs/reference/environments.md` so the third leg stops being invisible
  (S). Add a `rabbitmq` service to the CI `tests` job and let the queue integration tests run against
  it (M). Change `env_file` to `.env` and align the published port to 5000, or document 8001 as
  intentional (S). Fix the `Dockerfile.dev` comment (S).
- **Effort:** S for three of four; M for CI RabbitMQ coverage.
- **Evidence:** `docker-compose.yml:34` — `image: redis:alpine`, no tag.
  `.github/workflows/backend-ci.yml:121` — `image: postgres:15` against `docker-compose.yml:3`
  `image: postgres:17-alpine`. `docker-compose.yml:86-87` — `env_file:` / `- .env.development`;
  `test -f .env.development` → absent.

### Factor XI · Logs — treat logs as event streams (Violated)

- **Status:** Fail — **P0** · → [ADR-0041](../../../explanation/decisions/adr-0041-logs-as-event-streams-on-stdout.md)
- **What the code does:** Everything about the log _content_ is right. `src/utils/logger.ts:54-70`
  composes `timestamp()`, `errors({ stack: true })`, `splat()`, `attachRequestId()`,
  `redactSensitive()`, and `json()`, with `defaultMeta: { service: APP_NAME }`. Request correlation
  works through `AsyncLocalStorage` ([ADR-0027](../../../explanation/decisions/adr-0027-asynclocalstorage-for-request-correlation.md))
  so every line within a request shares a `requestId`, and sensitive values are masked recursively
  ([ADR-0028](../../../explanation/decisions/adr-0028-sensitive-key-pattern-out-of-envmanager.md)).
  This is well-formed, machine-parseable, correlated, redacted output.
- **Gap:** **It goes to the wrong place, and in production it goes nowhere else.** The logger
  declares exactly two transports, both files (`logger.ts:65-68`), and adds a Console transport only
  outside production:

  ```ts
  transports: [
    new transports.File({ filename: "logs/error.log", level: "error" }),
    new transports.File({ filename: "logs/combined.log" }),
  ],
  // …
  if (nodeEnv !== "production") {
    logger.add(new transports.Console({ format: combine(colorize(), logFormat) }));
  }
  ```

  So under `NODE_ENV=production` the app writes only to `logs/error.log` and `logs/combined.log` and
  **emits nothing to stdout**. Three consequences follow mechanically:
  1. The files sit on the container filesystem. On Render that filesystem is ephemeral — every
     restart, deploy, and instance replacement discards them. No volume is configured anywhere, and
     `logs/` is gitignored (`.gitignore` line 9).
  2. Neither transport sets `maxsize` or `maxFiles`, so both files grow without bound for the life of
     a container. The local copies are already at ~1.26 MB and ~650 KB.
  3. `docker-compose.yml` configures the `json-file` log driver with rotation on all four services
     (`:27-31`, `:46-50`, `:74-78`, `:101-105`) — collecting a stdout stream that, in production, is
     empty.

  Two further absences: there is **no HTTP access logging** (`grep` for `morgan` and `pino-http`
  across `src/` and `package.json` → no match), so request rate, latency, and status distribution are
  not recorded at all; and `scripts/logger.js` is a second, independent Winston instance that is
  Console-only, so the codebase disagrees with itself about where logs belong.

- **Why it matters:** This is the audit's only P0. A production incident today would be investigated
  with **no application logs** — they were written to a disk that no longer exists, and nothing was
  streamed anywhere. The request correlation, structured JSON, and redaction that the observability
  initiative built are all real work whose value is currently unrealised because the output has no
  route to a reader. It also blocks the pending decision directly: Loki collects log streams, and
  there is no stream.
- **Recommended fix:** See
  [ADR-0041](../../../explanation/decisions/adr-0041-logs-as-event-streams-on-stdout.md). The
  strict reading — the app writes to stdout only and never manages files — is the twelve-factor
  answer and the one this audit recommends, but the file transports were a deliberate choice
  recorded in the observability kit ("Winston file transports stay"), so reversing it warrants the
  ADR rather than a silent patch. Adding HTTP access logging is not a trade-off and should land
  regardless (S).
- **Effort:** S for the transport change itself; the decision is sized by ADR-0041.
- **Evidence:** `src/utils/logger.ts:72` — `if (nodeEnv !== "production") {` guarding the sole
  Console transport at `:73-77`. `src/utils/logger.ts:65-68` — the two `transports.File` entries,
  neither with `maxsize` or `maxFiles`.
  `grep -rn "morgan\|pino-http" src/ package.json` → no match.

### Factor XII · Admin processes — run admin tasks as one-off processes (Compliant)

- **Status:** Pass
- **What the code does:** Migrations are correctly separated from the run stage. The container
  command is `CMD ["node", "dist/server.js"]` (`Dockerfile:18`) with no migration step, and no
  application code invokes a migration at boot. Instead, CI runs them as discrete steps immediately
  before the deploy hook — `npm run migrate:staging:ci` (`backend-ci.yml:390`) and
  `npm run migrate:production:ci` (`:488`) — on a runner with a full `npm ci`, against the same
  `*_DATABASE_URL` the release will use. That is the textbook shape.

  The one-off toolkit is unusually complete: `scripts/db-migrate-test.mjs`,
  `scripts/seed-contract-tests.ts`, `scripts/bootstrap-fork.sh`, `scripts/generate-openapi.ts`, the
  three `scripts/security/*.mjs` gate scripts, and `scripts/test-ci.sh`, which runs the full suite
  inside a one-off `docker compose run --rm app` container built from the production image.

- **Gap:** One script contradicts the pattern. `start:staging` (`package.json:10`) chains
  `sequelize-cli db:migrate && node dist/server.js` into a single command, coupling the admin process
  to the long-running one. It is unused by both Docker and CI, and — per Factor II — would fail
  inside the runtime image anyway.
- **Recommended fix:** Delete `start:staging`; `migrate:staging:ci` followed by `start` already
  covers it and is what CI actually runs. Tracked under Factor II.
- **Effort:** S
- **Evidence:** `.github/workflows/backend-ci.yml:487-488` — `- name: Run DB migrations (production)`
  / `run: npm run migrate:production:ci`, as a step separate from the deploy trigger at `:496`.
  `Dockerfile:18` — `CMD ["node", "dist/server.js"]`, no migration.

## 5. Recommended sequence

1. **TF-1** (ADR-0041) — nothing else in observability is worth doing while production logs are
   discarded. It is also the cheapest of the three violations to fix.
2. **TF-6, TF-9, TF-11, TF-3** — four small, independent, non-controversial fixes with no pending
   decision blocking them. None is larger than S.
3. **TF-8, TF-10** — restore CI's evidentiary value before relying on it to gate the larger changes.
4. **TF-5** (ADR-0038) — the pending stack decision, now answerable because TF-1 gives it a stream
   to collect.
5. **TF-2, TF-4** (ADR-0039, ADR-0040) — the deployment topology changes. Largest, and both benefit
   from the decisions above being settled first.

## 6. What is already strong

Recorded so remediation does not erode it:

- Config centralisation — 65-key Zod schema, fail-fast boot, four raw `process.env` reads in the
  entire `src/` tree outside `src/config/`.
- The production `Dockerfile` — multi-stage, non-root, `dumb-init` PID 1, no config baked in. The
  Factor V problem is that it is unused, not that it is wrong.
- Graceful shutdown in both process types, including consumer draining in the worker.
- Liveness/readiness separation, with both probes mounted ahead of the rate limiter.
- Port abstractions where they matter — `MessageQueuePort` and `CachePort<T>` with real alternate
  adapters, not interfaces with one implementation.
- Migrations as one-off admin steps, never at container start.
- `docker-compose.test.yml` building the production `Dockerfile`.

## 7. Method notes and limitations

- **Line numbers are HEAD-relative.** Every citation was re-read against `638d75b` at write time.
  During the audit two subagent reports disagreed on `src/server.ts` offsets by roughly 25 lines;
  all `server.ts` citations here were re-verified first-hand as a result.
- **Absence findings** are stated as the exact command that returned nothing, so a re-auditor can
  reproduce them. They are the weakest evidence class in the report — a `grep` that misses a
  differently-named import would produce a false negative.
- **Production is not directly observable.** Render's managed Postgres and Redis versions, its
  filesystem persistence, and its log collection are not declared in the repo. Factor X item (1) and
  Factor XI's ephemerality claim rest on Render's documented default behaviour, not on inspection of
  the running environment. Confirming them against the Render dashboard would strengthen both.
- **Not re-graded here:** security posture, SaaS forkability, and performance — see §8.
