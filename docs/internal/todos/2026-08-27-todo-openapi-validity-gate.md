# Todo — validate the OpenAPI spec, not just its drift

Closes the gap that let PR #67 ship a structurally invalid spec to `dev`.

---

## What was wrong

`docs:openapi:check` is `generate && git diff --exit-code`. It compares the **generated** spec
against the **committed** one — so it detects _drift_, and nothing else.

A spec that is self-consistently wrong passes it perfectly: both sides contain the same defect, so
they match. That is exactly what happened. PR #67 added two dummy-endpoint operations referencing
`#/components/responses/TooManyRequestsError`, a component that was never defined. Three sibling
refs in the same block (`BadRequestError`, `UnauthorizedError`, `InternalServerError`) did exist, so
the fourth was assumed rather than checked.

Every gate stayed green — `docs:openapi:check`, lint, typecheck, the full test suite, newman, and
Schemathesis. Schemathesis reads the spec but did not fail on an unresolvable response `$ref` for an
operation outside its selected tag set.

**It broke a different repo.** `lakira-frontend`'s `api:types:generate` could not resolve the ref,
holding its api-contract job red on `dev` until PR #68 defined the missing component. This spec is a
contract another repo compiles against, which makes "the file did not change unexpectedly" a much
weaker guarantee than it looks.

## What changed

New `scripts/validate-openapi.ts`, wired into `docs:openapi:generate`, so it runs everywhere
generation runs — including inside `docs:openapi:check`. **CI therefore gets it with no workflow
change**, since `backend-ci.yml:67` already calls that gate. Also exposed standalone as
`npm run docs:openapi:validate` for checking the spec on disk without regenerating.

It checks:

1. **Every `$ref` resolves** against the document, by walking the JSON pointer — the class that bit
   us. External refs are rejected too; the spec is meant to be self-contained.
2. **Operation ids are unique** — downstream type generators key on them.
3. **Every operation declares at least one response** — an operation without one produces unusable
   client types.

Zero new dependencies. The spec is generated by zod-to-openapi, so broad structural validity is
already assured; the realistic failure mode is hand-written `$ref` strings in `registerPath`, which
this covers directly. A full validator (`@redocly/cli`, `@apidevtools/swagger-parser`) would catch
more, at the cost of a dependency in a repo that just spent a PR pruning them — worth revisiting if
a defect appears that this misses.

## Verification

The meaningful test was reproducing the original bug rather than asserting on the current spec:

1. Deleted the `TooManyRequestsError` component from `openapi-config.ts`, recreating the exact state
   PR #67 shipped.
2. Regenerated. **The new validator failed with both dangling refs and their precise locations:**

```
[OpenAPI] Specification is invalid — 2 problem(s):
  - dangling $ref "#/components/responses/TooManyRequestsError" at /paths//metrics/dummy/post/responses/429
  - dangling $ref "#/components/responses/TooManyRequestsError" at /paths//metric-categories/dummy/post/responses/429
```

3. Restored the component and confirmed the spec is byte-identical to the committed one and passes:
   `Validated 46 operations and 340 $refs. Specification is structurally valid.`

```
lint / typecheck / format:check   0
docs:openapi:check                clean, now including validation
test:unit / test:integration      green
```

## Not done

- **No unit test for the validator itself.** It is a build script with top-level side effects, and
  `scripts/` is untested by convention here. The reproduction above is the evidence, and it is
  repeatable. If this grows beyond three rules, extract the pure `validate()` into `src/lib/openapi/`
  and test it properly — a gate without a test is precisely the failure mode this todo exists to fix,
  so the exemption should not survive much more complexity.
- **Schemathesis not failing on unresolvable refs** for unselected operations is its own gap; left
  alone.
